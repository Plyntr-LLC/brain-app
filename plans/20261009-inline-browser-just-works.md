# In-app browser: just works (0.1.136)

Joe, 2026-10-09, after 0.1.135 shipped: the gaps listed with it "also need to be addressed. This must just work."

0.1.135 (`plans/20261008-inline-browser.md`) gave every Brain chat CLI brain-browser tools and showed the page in the thread. Left open: Grok, Cursor and Codex had no hard stop on Chrome; Google sign-in untested; the wide view is a picture polled every 0.5 s that takes only simple clicks and a few keys; Windows has no unix socket; the full packed app was never launched.

Facts found 2026-10-09 (probes on this Mac):
- control-chrome is configured only for Claude (`~/.claude.json`). Grok (`~/.grok/config.toml`), Cursor (no `~/.cursor/mcp.json`) and Codex (`~/.codex/config.toml`) have no Chrome MCP. Grok's built-in tools have no browser tool (only `web_fetch`). Their remaining ways to Chrome are shell commands: `open <url>` (also used by `python -m webbrowser` and the npm `open` package) and the brain's WhatsApp script `code/whatsapp/wa.cjs`, which launches headed Chrome by design. The brain's runbook (`personal/claude-local/machine.md`) tells agents to use wa.cjs for WhatsApp.
- Google sign-in in the in-app browser (Chrome UA, offscreen view): entering joe@plyntr.com moved on to "Verifying it's you… Complete sign-in using your passkey" with "Try another way". No "This browser or app may not be secure" block.
- Electron honours `--user-data-dir`. Brain's launch reads the Agency Brain config from `os.homedir()` and starts brain sync on the folder it finds, so a test launch with the normal HOME would sync Joe's real brain beside his running Brain. A test launch must use a temp HOME as well as a temp userData.

## 1. Behavior when done

1. **No Chrome from a Brain chat.** Every AI chat process Brain starts gets `chatEnv()`: `BRAIN_CHAT=1` and `<userData>/chat-shims` first on `PATH`. That is Claude's per-tab process, the Grok/Cursor ACP chat processes, the chat Grok leader (which also serves Show terminal's Grok TUI, since that TUI is the same chat), the Codex app-server, and Show terminal / Skin CLI TUIs (`pty:create` with a `kind`). A plain shell Terminal tab (`pty:create` with `shell`), Factory and Desk keep their env and PATH as today. The `open` shim (`#!/bin/sh` that runs `src/main/open-guard.cjs` with Brain's executable and `ELECTRON_RUN_AS_NODE=1`; shipped in `extraResources` like `browser-mcp.cjs`) looks at every argument. If any argument is an `http(s)://` address, it refuses with "Brain chats do not open web pages in Chrome. Use the browser_open tool (brain-browser): it opens the page inside Brain and shows it in this chat." and exit 1, whatever `-a` app was named. Two cases pass through to `/usr/bin/open` (or `BRAIN_OPEN_BIN` in the check) unchanged: no web address at all (files, folders, apps), or every web address is a command-line sign-in link. A sign-in link is decided on the parsed URL, not a substring, and needs both: (a) its host is a known sign-in host (`github.com`, `vercel.com`, `dashboard.doppler.com`, `supabase.com`, `railway.com`, `railway.app`, `cursor.com`, `claude.ai`, `console.anthropic.com`, `accounts.google.com`, `dash.cloudflare.com`, `accounts.x.ai`, `auth.x.ai`, `auth.openai.com`, `login.microsoftonline.com`, `app.netlify.com`), and (b) it is an OAuth request (query has `client_id` with `response_type` or `redirect_uri`) or its path equals a CLI login path (`/login/device`, `/oauth/device`, `/oauth2/device`, `/device`, `/cli/login`, `/cli-login`, `/dashboard/cli/login`, `/loginDeepControl`) or starts with `/workplace/auth/cli/`. Every web address in the call has to be one; one ordinary page refuses the whole call. The refusal adds: "If this is a sign-in link for a command-line tool, ask the person to open it."
2. **wa.cjs stays out of the screen inside Brain.** The guard sits at the top of `openContext`, the one function every launching command goes through (`link`, `status`, `read`, `voices`, `reply`, `send`, `batch`, `stay`), before `launchPersistentContext`. With `BRAIN_CHAT=1` and no new `--window` flag, it prints "Inside Brain, use the brain-browser tools on https://web.whatsapp.com (one shared login, shown in this chat). Add --window only if the person asked for a Chrome window." and exits 2. `list` and `self-test` never reach it. With `--window`, or without `BRAIN_CHAT` (terminal, Grok Bot, Desk runner), nothing changes.
3. **The brain's own instructions agree.** `AGENTS.md` working preference 11 gets one sentence: in a Brain.app chat, web pages, including WhatsApp Web, go through the brain-browser tools, not Chrome, control-chrome, Playwright windows, wa.cjs, or `open`. The WhatsApp section of `personal/claude-local/machine.md` says the same and keeps wa.cjs for terminal and Grok Bot use. The memory note about wa.cjs windows is updated.
4. **WhatsApp's login page is a sign-in.** A page with a QR login canvas (`canvas[aria-label]` matching /QR code/i, which is how WhatsApp Web draws it) counts as a sign-in, the same as a password field or a sign-in title: the thread shows "Sign in, in the browser." with Open browser, and the tool tells the agent to ask the person. A logged-in WhatsApp, or any page that only mentions "Scan to log in" in its text, is not a sign-in.
5. **The wide view is live.** While a picture is wide and its chat tab (or Desk) is active, the renderer holds a watch on that owner (`browser:watch(owner, true)`), and main streams the offscreen `paint` frames of the window that owner is showing as `browser:frame {owner, url, src}`, resized to 1100x800, at most 15 a second. Paint events fire only when the page changes, so a quiet page sends nothing. When the owner's shown window changes (it opens WhatsApp), main moves the watch to that window. The renderer drops the watch when the picture leaves wide, the tab goes inactive, the picture unmounts, or the owner closes. Small pictures keep the 1.5 s poll. Desk's picture gets the same watch.
6. **The wide view takes real input.** Mouse: the wide `<img>` is `draggable={false}`; mousedown, mousemove (about 30 a second, carrying the held buttons) and mouseup on it go to the page at the mapped point with `button`, `buttons` and `clickCount`, so drag-select, hover menus and double-click work. Keys: the focused wide picture's `keydown` handler sends every key to that owner's page (`browser:key(owner, { key, code, modifiers, text })`): printable text, Enter, Tab, Shift+Tab, Escape, Backspace, Delete, arrows, Home, End, PageUp, PageDown, with modifiers; Cmd (Ctrl on Windows) + A, C, V, X, Z and Shift+Z become the page's select all, copy, paste, cut, undo, redo. It calls `preventDefault` on every key it sends, which on macOS also keeps the app's Edit menu from acting on Cmd+V, C, X, A, Z (the renderer gets a key equivalent before the menu does). Main sends them to the offscreen page over CDP; paste reads the Mac clipboard there. (A `before-input-event` design was probed and dropped: it never sees CDP-injected keys, so no check could reach it.) The small picture still only widens on a click. Same layout and controls (working preference 13); Desk's picture gets the same input.
7. **Windows.** `startBrowserBridge` listens on `socketPath(platform, dir, pid)`: on win32 a named pipe `\\.\pipe\brain-browser-<pid>-<random hex>` with no chmod and no file sweep; elsewhere the 0600 `<dir>/browser-<pid>.sock` as today. The platform is a parameter defaulting to `process.platform`.
9. **The packed-app test launch cannot update itself.** `startAutoUpdate` returns early when `BRAIN_APP_NO_AUTO_UPDATE=1`. Only the live check sets it.
8. Google sign-in works in the in-app browser (probe above). A passkey prompt may not work inside Brain; "Try another way" (password or phone prompt) does. Said in the release notes, not changed in code.

## 2. How this can fail

H1. The shim is not on the PATH a CLI's shell commands actually use (Grok runs commands in its leader; Codex threads may filter env), so `open https://…` still opens Chrome.
H2. The shim blocks ordinary `open` of files or apps, or a CLI tool's own sign-in link.
H3. Agents asked in plain words ("open example.com and tell me the heading", "check my WhatsApp") still reach for wa.cjs, `open`, Playwright, or nothing, instead of the brain-browser tools.
H4. `BRAIN_CHAT` leaks into Desk, Factory, Grok Bot or the terminal and blocks wa.cjs there.
H5. wa.cjs's guard runs after Chrome has already launched.
H6. WhatsApp's QR page is not flagged as a sign-in, or a page that merely mentions it is.
H7. Wide frames never arrive, arrive for the wrong owner, keep streaming after the picture leaves wide, or show the old page after the owner switches to WhatsApp.
H8. Pointer events land at the wrong place (scale), drags lose the button, double-click is two single clicks, keys or shortcuts do nothing, paste pastes nothing.
H9. The live input change moves or restyles the picture's controls (preference 13).
H10. The Windows pipe path is built wrong, or the mac path changes.
H11. In the packed app, end to end, the picture never appears under the message, or clicks and keys from the real renderer do not reach the page.
H12. The test launch of the packed app touches Joe's real brain, userData, Grok leader, or auto-update.
