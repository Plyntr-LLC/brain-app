## 1. Behavior when done
A. Guide notes never pick a repo from README/package.json alias words. A note still moves the run by path, by folder name (whole word, hyphen pair like "mail desk", email->mail synonym, unique folder-name prefix/contains). The task at Start and task-based reconcile keep alias matching. Existing RT 1-6, WR 1-2, GF 1-2 keep passing unchanged.
B. Each run keeps `repos: {repo, base}[]` (every repo it has been in; seeded at Start, appended on each move). Before each builder turn, controller snapshots porcelain (status+content hash) of every candidate repo other than the current one: the run's earlier repos plus the repo the task itself resolves to. After a turn that changed nothing in the current repo, if a candidate's porcelain changed during the turn, the run moves there instead of retrying: lock moves (refused -> current behavior), workRepo/base become that repo's history base (or HEAD if not in history), profile re-read, warm=false, every Guide note read so far gets repo = the healed repo (so reconcile will not flip it back), card line `moved` says "Moved back to <name>: the last turn's edits landed there." Then the normal audit/verify continues. No candidate changed -> existing one-retry-then-pause behavior, unchanged.
C. strictPrompt adds: items no edit in this repo can close (split into separate changes/PRs, human sign-off, live runs that cost money or send mail, before/after on real data, deploy/ops steps) go in an `OUTSIDE:` block of `- ` bullets placed before the GAPS line; they are not gaps and do not make the verdict FAIL; a defect in the diff is never OUTSIDE. Controller splits the OUTSIDE block off (new `splitOutside` in opus.ts) before reviewAccept, stores bullets on `run.followUps` (cap 12 x 300 chars), saves the review file and strict.text without the block (so fix turns never chase them). Card shows them as a tiny list in the verify block: "Follow-ups outside this change". A review with only OUTSIDE items + GAPS: 0 + PASS is a pass. OUTSIDE words ("follow-up") never trip LEFTOVER because the block is removed first. A GAPS/PASS line inside the block still ends the block.
D. At Start and on every repo move, `pushWarn` is set: no remote named profile.publish.remote -> "No remote named origin. Factory commits here but cannot push."; else if shipThrough and current branch is protected -> "On main. Ship in advance commits but Brain never pushes main." Shown as a tiny line under the Approve/Ship lines. No behavior change to Push itself.
Existing screens stay: only new tiny lines inside the current card, no layout changes.

## 2. Ways this can fail (written before code)
F1 alias skip leaks into Start/task reconcile, so "Fix the typo in the Plyntr email footer"-type tasks or README-only names stop resolving.
F2 a note that should move (RT 2 "This is the email system for Plyntr", WR 1 kennel complaint, WR 2 "mail desk") stops moving.
F3 heal flips back: after moving back, the next reconcile re-reads the stored bad note and moves away again.
F4 heal fires on pre-existing dirt (files dirty before the turn) or on the brain repo or on a repo another run holds; or it steals from another run's lock.
F5 heal breaks GF 1 (plain empty turn must still retry once then pause) or GF 2.
F6 restored old runs without `repos` crash or heal wrongly.
F7 reviewer dumps a real code defect into OUTSIDE and it passes -- mitigated only by prompt; a FAIL verdict or GAPS>0 still fails regardless of OUTSIDE.
F8 OUTSIDE parse eats the GAPS/PASS lines or content after the block, turning a FAIL into a pass; or a missing block changes existing reviewAccept results (existing opus tests must pass unchanged).
F9 followUps from an earlier review linger after a later review with none (must be replaced each review, cleared when strict clears).
F10 pushWarn wrong for a repo with remote on a feature branch (must be none), or not refreshed after a move.
F11 snapshotting many repos slows turns (bounded: history + 1).
